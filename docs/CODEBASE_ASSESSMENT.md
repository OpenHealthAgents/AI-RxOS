# AI-RxOS Codebase Assessment

## 1. Executive Summary

AI-RxOS is an established pnpm/Turborepo monorepo with working infrastructure slices, not a blank project. Substantive reusable implementations exist for authentication, graph CRUD/versioning, scientific-source connectors and extraction, OpenSearch-backed search, a durable LLM Wiki, and a tenant-aware LangGraph agent runtime. These capabilities are unevenly integrated, and their existence does not establish end-to-end product readiness.

The user-facing Next.js applications remain starter screens. Several Compose-routed services (`ai-services`, `workflows`, `reports`, and `docking`) are in-memory references or stubs. Literature has real connector and processing code but also fallback JSON/in-memory paths and incomplete tenant-bound persistence. Search combines OpenSearch with process-local QMD and optional graph/citation enrichment; its tenant scope and failure behavior are not consistently enforced. The graph has useful CRUD/import/version concepts; Phase 2 now adds a canonical PostgreSQL identity/provenance/observation foundation, but source reconciliation and verified cross-store delivery remain incomplete.

The highest-priority risks before data-bearing future phases are tenant identity propagation and fail-closed enforcement, unclear ownership between overlapping auth/graph/agent facades, volatile or incomplete durable workflows, and mismatched contracts/configuration. Phase 2 has begun as an additive KG-owned canonical PostgreSQL model; source reconciliation and end-to-end projections remain incomplete. Preserve current service owners and evolve through explicit contracts, compatibility tests, and small migrations.

This assessment is based on repository source, tests, configuration, and documentation inspection. It does not claim a clean runtime deployment or production readiness. See the validation section for checks actually run.

## 6. Database and Data-Layer Assessment

### Existing reusable structures

- **PostgreSQL:** Auth organization/user/session/membership/workspace/project/API-key/audit structures; LLM Wiki pages/versions; literature paper/job tables; agent prompt-registry migration; and the new KG-owned `canonical` schema for entity identity, source records, aliases, identifiers, relationships, observations, and projection outbox. The canonical schema is an additive system of record in the existing shared database.
- **Neo4j:** graph domain labels include `Gene`, `Protein`, `Disease`, `Drug`, `Target`, `Mutation`, `Publication`, `Patent`, `ClinicalTrial`, `Company`, `Conference`, and `Biomarker`; indexes/unique ID constraints, source/evidence/confidence and graph version concepts exist in `services/kg`.
- **OpenSearch:** search service creates/manages its index and exposes lexical query, bulk indexing, and hybrid retrieval contracts.
- **Redis:** auth session/refresh/rate-limit use and agents streams, checkpoints, task state, locks, and conversation/memory keys are implemented. Literature jobs do not use a durable Redis queue in the inspected orchestrator.
- **LLM Wiki:** versioned page/document/entity/summary/relationship/evidence/chunk/provenance JSONB records provide reusable knowledge persistence, but these are not a normalized canonical evidence model.

### Gaps and integrity risks

- The new canonical schema provides stable IDs, exact namespaced identity, provenance, append-only observations, and temporal fields. Full source-to-canonical reconciliation, conflict review, derived-feature lineage, and recommendation snapshots remain missing.
- Literature creates a minimal schema in application code. Its paper rows do not carry tenant/source-raw payload/provenance/temporal fields from the future target, and the paper list/detail SQL has no tenant predicate.
- Migrations are service-specific/incomplete; no unified migration orchestration or cross-store consistency/outbox path was found. Literature's Postgres and local queue may diverge on restart or multi-replica deployment.
- LLM Wiki uses one natural key for org/workspace/category/slug and version JSONB; its tenant control is stronger than other paths but still treats organization as opaque caller input and permits global/NULL-owned pages.
- Neo4j versions support a max-version view, not event-time/valid-time temporal evidence or immutable source observations. Node identity derived from category/text is deterministic but not a domain-grade source-to-canonical resolution process.
- OpenSearch/QMD synchronization has no inspected durable reindex/replay ledger. Process restart loses QMD state; bulk/index provider errors can be swallowed.
- Soft deletion/audit/versioning are inconsistent across owners. No unified transactional boundary can atomically persist evidence, graph state, search index, and wiki pages.
- PostgreSQL `pgvector` is enabled by Compose, but current search docs/code disagree about whether it is an active retrieval backend; it should not be adopted as a second search owner without a measured decision.

**Classification:** canonical data model — PARTIAL / Phase 2 in progress; per-service persistence — PARTIAL; LLM Wiki persistence/versioning — IMPLEMENTED; local global graph/search projection — PASS; managed deployment projection configuration and tenant-private graph/search projection — unverified/deferred until downstream tenant enforcement exists.

## 7. Authentication, Authorization, and Tenancy

### Authentication

- BetterAuth handlers/plugins, password/social configuration, sessions, organizations, MFA, passkeys, SSO/SCIM, API keys, JWT-related utilities, key management, and rate/brute-force controls exist in `services/auth`; a separate adapter and retained Go auth source are documented in Section 5.
- The gateway validates bearer tokens with HS256 for protected prefixes. Literature independently decodes JWTs; agents independently validates tokens with issuer/audience checks in production settings.
- LLM Wiki uses optional bearer API-key authentication. When no key is configured it accepts unauthenticated requests; the Compose default is empty.
- **Classification:** authentication foundation — PARTIAL because deployed issuer/token ownership and the frontend-to-gateway login flow are not unified.

### Authorization

- Auth includes RBAC helpers, ABAC evaluation, role-protected admin routes, and audit records. Agents checks selected tool permissions, agent allowlists, job ownership, conversation/memory ownership, and replay roles.
- KG, Search, workflows, reports, docking, and the knowledge/AI facades have routes without service-local authorization in the inspected paths. Gateway middleware applies a bearer check to routed requests but is bypassable through direct service exposure and does not add a service identity assertion.
- **Gateway identity propagation gap:** `apps/api-gateway/internal/gateway/middleware.go` validates tokens but does not attach verified claims downstream; `apps/api-gateway/internal/gateway/proxy.go` adds only `X-Forwarded-Gateway`. Gateway checks HS256/token validity but not issuer/audience like agents production mode. No common service-to-service authorization contract was found.
- **Classification:** RBAC/ABAC foundations — PARTIAL; uniform API/service authorization — MISSING.

### Tenancy

- Agents derives organization/workspace/user from validated JWT claims and scopes selected Redis payload/task/memory operations. Wiki passes org/workspace scope into repository queries and applies RLS, while allowing global/NULL-owned pages.
- Auth RLS policies explicitly permit rows when tenant context is NULL. Auth/legacy paths use inconsistent GUC names (`app.tenant_id` versus `app.organization_id`); TS db wrappers may omit or ignore tenant-setting errors. Search accepts body tenant values, does not scope lexical search uniformly, and zero-tenant QMD scope sees all documents. Literature paper/job SQL and KG queries do not consistently include tenant predicates.
- **End-to-end trace:** current web page sends no request. In the configured future path, browser bearer → gateway JWT validation → proxy leaves identity claims unforwarded → service-local checks vary → SQL/Neo4j/Search queries have missing or optional tenant scope. Tenant identity does not have a verified end-to-end path.
- **Classification:** tenant foundations — PARTIAL; fail-closed cross-service tenant isolation — MISSING. No redesign is performed in this phase; migration/test requirements are in the risk/evolution registers.

## 8. Search and Retrieval Assessment

- OpenSearch provides a real lexical index/query and indexing API. The Go service offers `GET` lexical and `POST` hybrid endpoints, stream/context routes, citation/graph enrichment hooks, and a configurable Reciprocal Rank Fusion ranker.
- Dense similarity and local BM25/QMD are implemented in an in-memory `QMDEngine`; each retrieval-provider instance owns its own engine. Provider code makes optional remote calls but suppresses network/status/decode failures as empty results. Index code ignores provider and OpenSearch bulk errors and may return success regardless.
- Query tenant values are body fields on hybrid calls. Lexical OpenSearch queries do not use those fields in the inspected handler. QMD's compatibility zero-tenant query sees all documents, and shared/untentanted docs are visible to all scopes. This is not a complete tenant boundary.
- Search results are page-one/limit responses without a durable cursor or unified filtering contract. Index payload support is flexible but does not provide a verified idempotent provenance/reindex ledger.
- Literature integration calls the shared indexing API; KG graph enrichment exists as an adapter. Citation authority data is in-process and requires verification of its population/lifecycle.
- There is no distinct typed API/product contract for asset, evidence, publication, trial, patent, company, target, or disease search, and no tested cross-domain hybrid policy.

**Classification:** core lexical/hybrid implementation — PARTIAL and reusable; durable semantic retrieval/reindexing — PARTIAL; tenant-safe hybrid retrieval — PARTIAL; target Asset/Evidence search families — MISSING. Extend the existing search owner; do not add another index/service.

## 9. Knowledge Graph Assessment

- `services/kg` is the Neo4j owner and now also owns the additive canonical PostgreSQL schema, API, migrations, and global projection worker. The schema includes target-agnostic entity families, namespaced identifiers, sourced aliases, relationships, append-only observations, temporal/source timestamps, and an outbox.
- Existing generic Neo4j labels remain migration inputs; legacy graph routes are not all tenant-authorized. Canonical name collisions are retained and exact lookup reports ambiguity. Full source reconciliation, contradiction review workflows, temporal as-of reconstruction, and tenant-private graph projection remain incomplete.
- `apps/knowledge-service` is a second direct Neo4j read API for entities/neighbors, bypassing the KG service boundary and duplicating graph access. The graph legacy Cypher route performs read intent checks using keyword filtering and returns exception text; it should remain restricted and be reviewed before external exposure.
- Literature has graph-client integration and deterministic entity ID code, but no confirmed source-to-canonical entity-resolution workflow.

**Classification:** graph persistence/query/import/version foundation — PARTIAL; canonical PostgreSQL identity/provenance/observation foundation — PARTIAL; global graph projection — implemented but awaiting live Search side validation; tenant-private graph projection — deferred; duplicate knowledge facade — CONFLICTING. Keep `services/kg` as owner and migrate/retire only overlapping facade behavior after compatibility testing.

### Processing and operations

The service includes normalization, parsing, document deduplication, NER/relationship extraction, summarization, evidence ranking, search indexing, graph/wiki integrations, retries and metrics. Tests exercise substantial pipeline and integration behavior. Ingestion is therefore more than documentation, but it is not a target-complete evidence platform.

The API has two persistence modes: PostgreSQL tables dynamically ensured by `PostgresManager`, plus in-memory paper/job caches and a JSON-backed `JobStore` fallback. The orchestrator uses an in-process `asyncio.Queue`, scheduler task and worker task; some job state is persisted to Postgres, but queue ownership, multi-worker claims and tenant scoping are not durable/consistent. The public contract in `services/literature/API_CONTRACT.md` describes more endpoints/fields than the routers implement. ## 22. Technical Debt

- Multiple versions/owners coexist for auth, graph reads, and agent task APIs without a completed migration plan.
- Docs and executable contracts drift; old phase numbering and capability wording can lead to premature implementation.
- Literature schema is dynamically created rather than managed as a complete migration set; there are two job persistence modes and an in-process worker/scheduler.
- Process-local QMD, workflows, reports, docking, and facade state are not multi-replica durable.
- Cross-service API request/response, tenant, trace ID, pagination, structured error, and retry semantics are inconsistent.
- Broad `Any`/JSON payloads and generic labels/relationships make future data evolution difficult without contract fixtures.
- Production settings contain placeholders and local default secrets; no demonstrated live operations evidence accompanies deployment claims.

## 23. Security Risks

1. RLS policies explicitly allow access when tenant context is absent in auth; application settings are inconsistently named/set.
2. Gateway does not propagate verified identity/tenant claims; multiple backend services lack independent authorization or tenant checks.
3. Search accepts tenant fields from request payloads and does not consistently filter lexical/query/index operations; zero tenant QMD scope intentionally sees all data.
4. Literature jobs/papers and KG endpoints do not consistently scope SQL/graph operations by authenticated tenant.
5. LLM Wiki API-key enforcement is optional and Compose defaults the key to empty; internal endpoint exposure must be restricted or configured.
6. Compose exposes stateful database ports and includes default credentials; those values must never be reused outside local development.
7. Helm production values include placeholder hosts and must not be applied unchanged.
8. Separate auth implementations risk accepting different token claims/sessions and leaving legacy endpoints exposed. Direct service ports bypass gateway checks in Compose-like deployments.
9. Search/index handlers can obscure backend failures as empty/success outcomes, which risks silently serving incomplete evidence.

No claim is made here that each risk is externally exploitable in a particular deployment; deployment exposure and credentials determine impact. These are code/config paths that require closure before production data is trusted.

## 24. Data Integrity Risks

- Canonical IDs and source-linked observations now exist for new records; existing Literature/Neo4j/Search records are not yet reconciled to them.
- Source dates/cursors and raw payload lineage vary; fixed preprint query windows may omit new updates.
- In-memory/JSON fallback paths can lose or diverge from Postgres state; process-local queues lack transactional delivery.
- Search indexing, graph updates, wiki writes and source persistence are not coordinated by an outbox or replayable event ledger.
- Errors swallowed in search indexing/retrieval can make stored/indexed evidence disagree without a visible job failure.
- Graph version number is not equivalent to historical truth validity; no audited as-of evidence snapshot exists.
- Source duplication and cross-domain entity resolution have no demonstrated end-to-end contract.

## 25. Architectural Risks

- Multiple service owners overlap, especially auth (`services/auth`, `auth-adapter`, legacy Go sources), graph (`services/kg`, `apps/knowledge-service`), and agents (`services/agents`, `apps/ai-services`).
- Runtime behavior varies by Compose/Helm/local path; documentation does not always identify which binary/image is active.
- Future evidence and decision services could duplicate current graph/search/wiki/agent capabilities unless they attach to named service owners.
- Contract-level workflow/reporting APIs may be mistaken for production capabilities and feed user decisions with volatile or fabricated statuses.
- Target models, ranking/scoring, and production capacity claims are not test-backed yet.

## 26. Recommended Migration Sequence

This is a dependency-aware sequence. Phase 2 is currently authorized and in progress; later phases remain unauthorized by this implementation request.

1. **Complete Phase 2 — Canonical Data Model:** current additive KG/PostgreSQL identity, source, observation, API, and local projection contracts are in place; finish source reconciliation, API compatibility review, and migration/count/rollback validation. Do not replace current tables.
3. **Tenant/security prerequisite:** before cross-tenant canonical data is loaded, normalize identity claims/settings, propagate verified identity, enforce service-local scope, make RLS fail closed, and add end-to-end isolation tests.
4. **Durable evidence intake:** extend literature persistence/jobs with idempotency, source provenance/cursors, retries/dead letters, and owner-specific migrations; integrate search/KG through explicit versioned contracts.
5. **Canonical graph and search attachment:** resolve existing graph nodes and search documents to canonical identities; persist/replay indexes and filter by authorization scope; retain existing APIs during migration.
6. **Derived features and engines:** implement only after evidence/temporal contracts, representative fixtures, uncertainty, provenance, and leakage tests exist.
7. **Decision/review:** add recommendation snapshots, explanation, human review/override and audit trails after engine outputs are reproducible.
8. **Product workflows and operations:** connect existing UI/agent runtime to stable APIs, replace only reference implementations with justified durable workers, and demonstrate observability, backup/recovery, security and deployment gates.

## 39. Technical Debt and Recommended Evolution Sequence

Technical debt includes duplicate auth source/runtime, overlapping graph and AI facades, active/inactive connector registries, mismatched settings and route schemas, volatile fallbacks, runtime-created literature DDL, process-local QMD and stub endpoints, no unified migration/outbox/reindex path, inconsistent pagination/error/trace contracts, and stale architecture/configuration statements. Recommended order (Phase 2 is currently in progress):

1. Complete the additive Phase 2 canonical contract and verify migrations/counts against existing owner schemas.
2. Before tenant data expansion, resolve identity/token ownership and fail-closed service/database boundaries with compatibility tests.
3. Reconcile existing source-specific records by exact namespaced IDs; retain unresolved/ambiguous candidates, old IDs, and rollback path.
4. Then add source/evidence/temporal contracts and durable literature jobs without replacing tested connectors.
5. Evolve the current KG and Search owners to canonical projections with idempotent indexing, scope filters and replay.
6. Add derived features and domain intelligence only after evidence snapshots, temporal cutoffs and evaluation fixtures exist.
7. Add recommendations/human review after predictions are reproducible; connect existing UI and agent runtime to the resulting APIs.
8. Validate deployment, backup/restore, centralized telemetry, external integrations and end-to-end security before any production-readiness claim.
